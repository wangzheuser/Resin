## 二、历史问题：动态 TCP 端口占用（已缓解，仍有隐患）

**端口范围**：`netsh int ipv4 show dynamicport tcp` → 49152–65535，共 16384 个。

**当前占用**：三次采样（间隔 30s）

| 时间 | TIME_WAIT | ESTABLISHED | SYN_SENT |
|---|---|---|---|
| 10:04:51 | 3020 | 816 | 413 |
| 10:05:24 | 2864 | 765 | 409 |
| 10:05:58 | 2346 | 685 | 411 |

动态端口占用率在 10%–18% 之间**波动而非单向增长**，峰值约 3000/16384，未接近耗尽。**结论：端口耗尽风险当前不存在。**

**但连接 churn 很高**，是隐患来源：

- `com.docker.backend.exe`（PID 18848）持有 **741 条连接**，其中 `SYN_SENT=395`（大量外连发起后无法建立）
- 对端正是日志中的代理节点：`185.255.179.11:9443`、`85.208.86.91:9872`、`31.56.189.27:2087`、`31.76.97.115:40604` 等
- 约 11 小时日志统计：
  - `route_failover`：retry 1868 / success 714 / **failed 177**
  - `failure_kind`：`eof` 1518、`network_error` 366、`timeout` 195、`http_status_error` 64
  - `probe` 每分钟失败数在 0–670 之间波动

**风险判断**：节点池越大、死节点越多，每次 failover 都新建连接，TIME_WAIT 持续累积。若节点池继续扩大或提高探针并发，有可能逐步逼近 16384 上限。当前 18% 属安全区间。

## 三、待处理问题

### 问题 1（确凿配置缺陷）：请求日志保留参数未生效

- `.env` 中已设置：
  ```
  RESIN_REQUEST_LOG_DB_MAX_MB=256
  RESIN_REQUEST_LOG_DB_RETAIN_COUNT=2
  ```
- 但 `docker-compose.yml` 的 `environment:` 段**未声明这两个变量**，导致容器内实际环境变量中完全没有它们（已用 `docker inspect` + 容器内 `env` 双重确认）。
- 服务因此仍使用内置默认值：`MAX_MB=128`、`RETAIN_COUNT=5`。
- 佐证：`/var/log/resin` 现有 **4 个** `request_logs-*.db`，合计 431.4MB，单文件约 125–127MB（正好卡在 128MB 上限），文件数 4 ≤ 5（默认保留数）——与默认配置完全吻合。
- 保留逻辑见 `internal/requestlog/repo.go:470 cleanup()`（启动时与轮转时各调用一次，按文件名排序保留最新 N 个）。

**修复**：在 `docker-compose.yml` 的 `environment:` 下补上：

```yaml
      RESIN_REQUEST_LOG_DB_MAX_MB: ${RESIN_REQUEST_LOG_DB_MAX_MB:-128}
      RESIN_REQUEST_LOG_DB_RETAIN_COUNT: ${RESIN_REQUEST_LOG_DB_RETAIN_COUNT:-5}
```

然后 `docker compose up -d resin`。重启时 `cleanup()` 会自动把日志裁剪到 2 个文件。

### 问题 2：MaxUserPort=15000 遗留配置

- 注册表 `HKLM\SYSTEM\CurrentControlSet\Services\Tcpip\Parameters\MaxUserPort = 0x3a98`（15000）。
- 与 `netsh` 动态端口范围 49152–65535（16384 个）语义冲突。实测临时端口均落在 49152+，说明当前以 netsh 范围为准，`MaxUserPort` 实际未生效。
- 该值应是此前排查端口问题时留下的，属潜在误配，建议删除以免后续误解或误调。

### 问题 3：TcpTimedWaitDelay 未设置

- 该注册表值缺失，Windows 默认 TIME_WAIT 为 120 秒。
- 在高 churn 场景下端口回收偏慢。若希望压低 TIME_WAIT 峰值，可设为 30–60 秒（`TcpTimedWaitDelay` DWORD）。

### 问题 4：高连接 churn 与无效外连

- 压力集中体现在 `com.docker.backend.exe`：741 连接、395 SYN_SENT、内存 350MB。
- 大量 `failure_kind=eof`（1518 次）说明对端主动断开或节点已死。
- **建议**：调大探针间隔 / 对连续失败的节点延长冷却与黑名单时长，减少对死节点的无效重连。

### 问题 5：运维遗留

- `docker-compose.override.yml` 将 `resin_cache / resin_state / resin_log` 三个卷 `external` 指向 `resin_restore_20260831_163016_*`（8 月 31 日恢复卷），即服务当前跑在恢复数据上。
- 旧的 `resin_resin_cache / resin_resin_state / resin_resin_log` 三个卷仍存在，占空间。
- **C 盘已用 93%，仅剩 35GB**，Docker Desktop 数据盘在 C 盘，镜像/卷增长有风险，需关注。

手动执行的注册表命令（管理员 CMD/PowerShell，执行后重启生效）：

```
reg delete "HKLM\SYSTEM\CurrentControlSet\Services\Tcpip\Parameters" /v MaxUserPort /f
reg add   "HKLM\SYSTEM\CurrentControlSet\Services\Tcpip\Parameters" /v TcpTimedWaitDelay /t REG_DWORD /d 60 /f
```

补充说明：重启后首轮会对全量节点池（约 2.6 万节点）做初始探针，日志中 `probe failure summary` 短时偏高（如 egress_fetch=599/min）属启动风暴，会自行回落。
